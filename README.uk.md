Вебзастосунок для зберігання, читання й поширення PDF-книжок у навчальному середовищі.
Вчитель завантажує матеріали, розкладає їх по теках і відкриває доступ класам або за посиланням.
Учні читають книжки просто в браузері й роблять власні виділення з нотатками, не змінюючи чужих файлів.

Працює на [pdf-share.website](https://pdf-share.website). Інтерфейс — українською та англійською.

### Інфраструктура

- **Власний сервер + Docker Compose** — три сервіси: `db` (Postgres 18), `web` (gunicorn + Django), `tunnel` (дві репліки `cloudflared`). Назовні не відкрито жодного порту.
- **Cloudflare Tunnel** — єдиний вхід. TLS закінчується на Cloudflare, трафік іде тунелем на `web:8000`.
- **Cloudflare R2** — приватний бакет для PDF, обкладинок і бекапів бази. Файли віддаються через короткоживучі підписані посилання, бо право на книгу перевіряє застосунок, а не сховище. Вмикається `USE_R2=true`; інакше файли лежать у `PDF+/media/`.
- **GitHub Actions** — CI на раннерах GitHub, деплой — на self-hosted раннері на сервері (див. [CI/CD і деплой](#cicd-і-деплой)).
- **Sentry** — єдиний трекер помилок і cron-монітор бекапів. Порожній `SENTRY_DSN` повністю вимикає SDK. Персональні дані в події не потрапляють. Реліз — хеш коміту, його задає `deploy.sh`.
- **Google OAuth** — акаунти зіставляються за поштою, тому email у моделі користувача унікальний.
- **SMTP** — листи скидання пароля. Налаштовується через `MAILERS` (Django 6.1); порожній `SMTP_HOST` друкує листи в консоль.

## Архітектура

Класичний монолітний Django-проєкт із серверним рендером. П'ять застосунків:

| Застосунок | Відповідальність |
|---|---|
| `users` | власна модель `User`, реєстрація, вхід паролем і через Google, профіль |
| `book_library` | теки (дерево через self-FK), книги, завантаження й перевірка PDF, обкладинки, читалка, каталог, правила доступу, прогрес читання |
| `sharing` | групи (класи), запрошення, членство, груповий доступ до книги чи теки, посилання з токеном |
| `annotations` | шари анотацій (один шар на користувача й книгу), виділення з нотатками, теми нотаток, публікація шару, JSON-API читалки |
| `api` | REST API на DRF: JWT, каталог, файл книги, дельта-синхронізація для офлайн-клієнта |

[![Architecture diagram](https://gitdiagram.com/diagram-badge.svg)](https://gitdiagram.com/illyadd/pdf-share?utm_source=readme&utm_medium=badge)

Ключові внутрішні модулі:

- `book_library/access.py` — єдине місце, що вирішує, хто що бачить. Усі в'юхи фільтрують queryset через `visible_books()` / `visible_folders()`.
- `book_library/pdf.py` — `inspect_pdf()` і для форми на сайті, і для адмінки: та сама перевірка, звідки б файл не прийшов.
- `book_library/signals.py` — видаляє файли зі сховища після `post_delete` і при заміні файлу (`pre_save`), відкладено до коміту транзакції.
- `book_library/progress.py` — `record_progress()` з last-write-wins за часом, коли читач був на сторінці.
- `annotations/validators.py` — сувора перевірка payload'у читалки перед записом у `JSONField`.
- `annotations/groups.py` — операції з темами нотаток, спільні для вебу й синку.
- `book_sharing_settings/health.py` — `/health/` для healthcheck'у Docker, відповідає ще до перевірки `ALLOWED_HOSTS`.
- `book_sharing_settings/dashboard.py` — статистика й 30-денний графік для головної сторінки адмінки.

## Можливості

### Користувачі

- Реєстрація з паролем або вхід через Google. У Google-акаунта пароля нема.
- Вхід через Google приймається лише з поштою, яку Google підтвердив. Якщо локальний акаунт з такою поштою існує, але адресу в ньому ніхто не підтверджував, його пароль скидається і вхід стає лише через Google — так ніхто не зареєструє чужу адресу заздалегідь, щоб потім читати чужі книги.
- Після реєстрації вітальна сторінка розповідає, що вміє сайт.
- Ролей нема: кожен користувач може завантажувати книги, створювати групи й ділитися. Права на матеріали визначаються власністю та наданим доступом.
- Профіль: перегляд, редагування, зміна пароля, видалення акаунта.
- Скидання пароля поштою (`/accounts/password/reset/`): посилання дійсне добу й спрацьовує один раз. Google-акаунти листа не отримують — пароля в них нема. На невідому адресу відповідь така сама, як на відому, тож формою не перевірити, чи зареєстрована пошта.
- Перемикач мови інтерфейсу (українська / англійська) і світла / темна тема.

### Бібліотека

- Дерево тек довільної глибини. «Хлібні крихти» й повний шлях («Батьківська / Дочірня / Онука») для тек з однаковими назвами.
- Завантаження PDF перетягуванням. Ліміт 50 МБ. Файли перевіряються по-справжньому: сигнатура `%PDF-`, розбір через PyMuPDF, відсів захищених паролем і порожніх документів.
- Назву вводить користувач, вона обов'язкова. При завантаженні зберігаються кількість сторінок, розмір файлу й прапорець текстового шару (від нього залежить, чи працюватиме виділення).
- Обкладинка рендериться з першої сторінки й показується на картках книг. Для книг, залитих до появи обкладинок: `manage.py render_covers`.
- Ключ файлу у сховищі — випадковий UUID, а не ім'я від користувача.
- Перейменування, заміна файлу, переміщення між теками, видалення. Масове додавання книг у теку.
- Пошук за назвою без урахування регістру з підтримкою кирилиці. Усередині теки пошук охоплює все піддерево.
- Розділи: «Моя бібліотека», «Поділилися зі мною», «Каталог».

### Каталог

Адміністратор позначає теку прапорцем `is_catalog`. Вона разом з усім вкладеним стає видимою кожному користувачу, що увійшов. Пошук у каталозі охоплює весь його вміст.

### Поширення

- **Групи (класи).** Вчитель створює групу й відкриває їй доступ до книги чи теки. Доступ до теки поширюється на все дерево під нею.
- **Вступ до групи — лише за згодою.** Додати когось напряму власник не може. Є два шляхи: посилання-запрошення (токен можна перевипустити, і старе посилання перестане діяти) або запрошення за username, яке користувач приймає чи відхиляє. Запрошення, що чекає відповіді, доступу не дає. Власник може скасувати запрошення й вилучити учасника.
- **Посилання з токеном.** Власник створює посилання на книгу чи теку, з терміном дії або без. Токен генерується `secrets.token_urlsafe(32)`. Відкрите посилання запам'ятовується в сесії, тож перехід між книгами працює без повторного введення.
- **Посилання з нотатками чи без.** Створюючи посилання, автор обирає «Лише книга» (за замовчуванням) або «Книга з моїми нотатками». Друге дає отримувачу — навіть анонімному — доступ лише на читання до шару автора на цій книзі (для теки — на кожній книзі піддерева), а кнопка на сторінці посилання веде одразу в цей шар. Шарів інших користувачів на тій самій книзі посилання не відкриває.
- **Теми в посиланні.** Для посилання на книгу з нотатками можна обрати окремі теми — отримувач побачить лише їх (без назв тем). Нічого не обрано — усі нотатки. Якщо всі обрані теми видалено, посилання не покаже жодної нотатки.
- Список власних посилань і наданих доступів з можливістю їх відкликати.

### Читалка

- Сторінки рендерить PDF.js у canvas, ліниве завантаження через `IntersectionObserver`.
- Масштаб від 50% до 300%, перехід на сторінку за номером, стрілки «попередня / наступна сторінка».
- Виділення тексту палітрою з п'яти світлих кольорів (`mix-blend-mode: multiply`, текст лишається читабельним).
- Нотатка до кожного виділення. Бічна панель зі списком анотацій і фільтром за кольором.
- Теми нотаток у межах книги: перемикач «Тема» в читалці визначає, куди йдуть нові виділення і що показано; нотатку можна перенести в іншу тему з поповера. Перейменування й видалення тем — на сторінці «Мої нотатки» (нотатки видаленої теми потрапляють у «Без групи»).
- Анотації зберігаються як список прямокутників у PDF user space, тому правильно масштабуються.
- Читати книгу може кожен, хто її бачить. Анотувати — лише користувачі, що увійшли. Шар кожного окремий і ніколи не змінює чужу книгу.
- Прогрес читання: поле сторінки на панелі інструментів стежить за прокручуванням, поточна сторінка зберігається
  (із затримкою 1,5 с і при закритті вкладки), і наступного разу книга відкривається на ній.
  На головній є блок «Продовжити читати»; на сторінці книги — прогрес і кнопка «Продовжити з с. N».
- Шар учителя для класу: власник групи може опублікувати свій шар на сторінці книги для обраних груп
  (лише тих, чиї учні бачать книгу — через доступ до книги, до теки над нею або каталог).
  Учні отримують у читалці перемикач «Мої / *ім'я вчителя*»: чужий шар лише для читання, без
  попапу редагування. Відкликання доступу до книги ховає й шар.

JSON-API читалки (сесійна автентифікація, CSRF як у форм):

```text
GET    /api/books/<id>/annotations/     анотації поточного користувача
GET    /api/books/<id>/shared-layers/   шари вчителів, опубліковані для груп користувача
POST   /api/books/<id>/annotations/     створити виділення
PATCH  /api/annotations/<id>/           змінити колір, нотатку чи тему (group)
DELETE /api/annotations/<id>/           видалити
GET    /api/books/<id>/note-groups/     теми поточного користувача в книзі
POST   /api/books/<id>/note-groups/     створити тему {name}
PATCH  /api/note-groups/<id>/           перейменувати тему
DELETE /api/note-groups/<id>/           видалити тему (нотатки → «Без групи»)
POST   /books/<id>/progress/            {page} — зберегти поточну сторінку (204)
```

### REST API (DRF, JWT)

Для мобільного / офлайн-клієнта. Заголовок: `Authorization: Bearer <access>`. Токен
перевіряється за підписом, сервер не ходить у базу. Access-токен живе 30 хвилин, refresh — 30 днів,
і ротується при кожному оновленні. Blacklist не ввімкнений: refresh-токен не відкликати достроково.
Видача й оновлення токенів обмежені 10 запитами на хвилину з однієї IP-адреси.
Сесій і CSRF тут нема, тож share-посилання (джерело 3 у моделі доступу) в API не працюють.

```text
POST   /api/v1/auth/token/          {username, password} → {access, refresh, user}
POST   /api/v1/auth/token/refresh/  {refresh} → {access, refresh}
GET    /api/v1/catalog/books/       каталог, пагінація по 50, ?search= за назвою
GET    /api/v1/books/<id>/file/     302 на файл у сховищі (з R2 — підписане посилання)
GET    /api/v1/sync/?since=<ISO>    дельта стану: books, folders, annotations (власні),
                                    deleted_annotation_ids, note_groups (власні теми),
                                    reading_progress, shared_layers, shared_annotations
                                    (шари вчителів), visible_book_ids, visible_folder_ids,
                                    server_time
POST   /api/v1/sync/                батч {note_groups: {create, update, delete},
                                          annotations: {create, update, delete},
                                          reading_progress: [{book, last_page, read_at}]}
```

Без `since` pull повертає повний стан. Клієнт зберігає `server_time` як наступний `since`
і викидає локально все, чого нема у `visible_*_ids` (відкликаний доступ, видалена книга).
Видалені анотації фіксуються тумбстоунами (`api.DeletedAnnotation`, через `post_delete`);
у `deleted_annotation_ids` потрапляють і видалення з опублікованих шарів учителів.
`shared_layers` щоразу йде повністю: шар, що зник зі списку, клієнт викидає разом з анотаціями.
Шар, що став видимим після `since` (нова публікація, вступ до групи, доступ до книги),
приходить повністю в `shared_annotations`.
У push кожна операція незалежна: помилки повертаються поштучно в `errors`, конфлікти
розв'язуються за last-write-wins. Для прогресу читання переможця визначає `read_at` (коли клієнт
був на сторінці), а не час приходу push'а: офлайн-телефон не затре новішу позицію з вебу.
`reading_progress` у відповіді — фактичний стан після злиття.

Теми нотаток у синку:

- `note_groups` у pull — **повний** список власних тем (`id, book, name, created_at,
  updated_at`) щоразу, навіть у дельті; тема, якої нема в списку, видалена. Тумбстоунів для тем
  нема. В анотацій є поле `group` (`id` теми або `null` — «Без групи»);
  у `shared_annotations` його нема — учні бачать нотатки вчителя без його тем.
- У push `note_groups.create` — `[{client_id, book, name}]`, `update` — `[{id, name}]`,
  `delete` — `[id]`. Створення за назвою ідемпотентне: якщо тема з такою назвою в цій книзі
  вже є (інший пристрій, повторний push), повертається саме вона з вашим `client_id`.
  Перейменування на зайняту назву — помилка операції `group_update`.
- Анотація в `create`/`update` приймає `group: id | null` або `group_client_id` — тему,
  створену в тому самому push'і. Тема має належати тій самій книзі.
- Порядок обробки: видалення тем → перейменування → створення → анотації → прогрес.
  Тож «видалити чи перейменувати X і створити новий X» в одному push'і дає нову тему.
  Якщо нотатка посилається на тему, видалену в тому самому push'і, вона потрапляє в «Без групи»,
  а решта її змін зберігається. Видалення теми не видаляє її нотаток — сервер переносить їх
  у «Без групи» й оновлює `updated_at`, тож вони приходять у наступній дельті.
- Результат push'а — `note_groups: {created, updated, deleted}`; помилки йдуть у спільний
  `errors` з `op` `group_create` / `group_update` / `group_delete`. Операції з темами
  враховуються в ліміті батча.

### Адмінка

- Unfold із власним `AdminSite`. Шлях адмінки задається в `.env` (`ADMIN_SITE_URL`), тому `/admin/` на проді не відкритий.
- Дашборд: кількість користувачів, власників груп, учасників груп, книг, тек, анотацій, груп, активних посилань. 30-денний графік із трьома рядами: нові користувачі, книги, анотації.
- Бейдж середовища (Development / Production).
- Завантаження PDF через адмінку проходить ту саму перевірку, що й на сайті.

## Модель доступу

Право на перегляд книги чи теки дає будь-яке з чотирьох джерел:

1. **Власність** — користувач є `owner`.
2. **Група** — матеріал відкрито групі через `GroupAccess`, а користувач — її учасник.
3. **Посилання** — користувач відкрив `ShareLink`, і токен лежить у сесії.
4. **Каталог** — тека з `is_catalog=True` або будь-яка вкладена в неї.

Змінювати (перейменовувати, видаляти, замінювати файл) може лише власник. `GroupAccess.EDIT` є в моделі, але поки не додає прав на сам матеріал.

Файли в R2 приватні. Посилання на файл підписане на 3600 с (налаштовується через `R2_URL_EXPIRE`), тож прямим посиланням перевірку доступу не обійти.

## Локальний запуск

Потрібні PostgreSQL і Python 3.13. Redis — за бажанням.

```bash
uv sync
cp PDF+/.env_example PDF+/.env      # заповнити SECRET_KEY, PG_*, DEBUG=true
cd PDF+
uv run python manage.py migrate
uv run python manage.py createsuperuser
uv run python manage.py runserver
```

Базу створюйте з ICU-локаллю (`--locale-provider=icu --icu-locale=uk-UA`), як на проді й у CI: з локаллю `C` кирилиця не складається в `lower()` / `ILIKE`.

Змінні середовища описані в `PDF+/.env_example`. Для входу через Google потрібні `GOOGLE_OAUTH_CLIENT_ID` і `GOOGLE_OAUTH_CLIENT_SECRET`. Для R2 — `USE_R2=true` і ключі `R2_*`. Для пошти — `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `DEFAULT_FROM_EMAIL`.

Після зміни рядків інтерфейсу оновіть переклади (потрібен GNU gettext):

```bash
cd PDF+
uv run python manage.py makemessages -l en --ignore='static/vendor/*' --ignore='media/*'
uv run python manage.py makemessages -d djangojs -l en --ignore='static/vendor/*' --ignore='media/*'
uv run python manage.py compilemessages
```

## Тести

```bash
cd PDF+
uv run python manage.py test --parallel
```

Тести ніколи не ходять у R2: сховище примусово перемикається на тимчасовий `MEDIA_ROOT` (`book_sharing_settings/testing.py`). Покрито: правила доступу, перевірку PDF, поширення й запрошення, анотації, REST API й синк, автентифікацію та адмінку.

## CI/CD і деплой

- **CI** (`ci.yml`, кожен PR і push у `master`): `ruff --select F`, перевірка забутих міграцій, тести на Postgres 18 і збірка Docker-образу.
- **CD** (`cd.yml`): після зеленого CI на `master` self-hosted раннер на сервері запускає `deploy.sh` саме для того коміту, що пройшов CI. Скрипт збирає образ, застосовує міграції окремим кроком (якщо вони впадуть, старий контейнер працює далі) і чекає на healthcheck `/health/`.
- **CodeQL** (`codeql.yml`): статичний аналіз Python, JavaScript і самих workflow-ів — на кожен PR і щотижня.
- **Бекапи**: `backup.sh` з cron щогодини робить `pg_dump`, копіює його в R2 і відмічається в Sentry Cron — пропущений бекап піднімає алерт.
